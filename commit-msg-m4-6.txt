refactor(m4-6): 用户划线/高亮笔记域下沉 domain/marking + data/marking

M4-5c 关闭 AI 域后的第一片。新建模块对 `domain/marking` + `data/marking`（`settings.gradle`
的 `include` 与根 `build.gradle.kts` 的 `kmpModuleTypes` **成对登记**），把 `book_marks` 表
的仓储从 `:core:data` 搬走，消费方只见端口与领域模型。

一、为什么是 `BookMarking` 而不是看起来更该做的 `Bookmark`

选片判据是**依赖闭包**而不是引用数：
- `Bookmark`（书签）闭包 **42 个文件** —— 含 `Restore.kt` / `Backup.kt`（按实体读写
  `bookmark.json`，有备份兼容面）、`BookmarkExporter`、以及共享模块
  `feature:reader:core` ⇒ 是好几片，不是一片。
- `BookMarking`（划线/高亮笔记）则四条都对得上模板的排序判据：**已有 `BookMarkingGateway`**
  （端口是搬家，不是新造抽象）、**已有 `SaveMarkingUseCaseTest` 护栏**、**无
  `companion object` 常量**（避开 M4-3 `AiArtifact` 那种「常量被 DAO 的 SQL 插值引用、必须
  两侧复刻」的陷阱）、**不进备份/恢复**（`help/storage` 里零命中，无兼容面）。

二、形态

- `domain/marking`：`BookMarking`（12 字段逐字照抄实体：全 `val`、默认
  `systemTimeMillis()`、**全字段判等**——实体也没有 `equals` 覆写）+ `BookMarkingGateway`。
  端口**沿用旧名**（本仓 60+ 个同形态 `XxxGateway`），落点从 `core:data` 的
  `domain/gateway` 挪到 `domain/marking`（与 `domain/ai` 的 `AiXxxGateway` 同律）。
- `data/marking`：`BookMarkingMapper` + `BookMarkingRepositoryImpl`。照抄迁移前每个方法的
  `withContext(Dispatchers.IO)`（与 M4-1/M4-2/M4-4 同侧，不向上一片看齐）；`flowByBook`
  的映射留在**流内**（`.map { it.toDomainList() }`），`flowOn` 位置也照抄。

三、两处与模板同律的判断

1. **`setEnabled` 零调用方 ⇒ 随片从端口删除**，底层 DAO 方法保留（那是 `data:database`
   的债）；`SaveMarkingUseCaseTest` 的假实现同步去掉该 override。
2. **端口可以「新增」方法来吸收 `:app` 仍持有的 DAO**：`ContentProcessor` 原先在渲染热路径上
   直连 `appDb.bookMarkingDao.getForChapterSync(...)`。本片给它加了
   `getForChapter(bookUrl, chapterIndex)`，调用方从「持有 DAO」变「持有端口」（经
   `GlobalContext` lazy 取，与该文件既有的 `otherGateway` / `readGateway` 同形），顺带消掉
   一条 `appDb.` 锚定的 legacy 计数。

四、删除与迁移

- 删除 `core/data` 的 `BookMarkingGateway.kt` 与 `BookMarkingRepository.kt`，**不留门面/
  typealias**。
- 13 个消费文件改 import（8 个 `:app` 主源 + 1 个测试 + `appModule` + 两个新模块自身）；
  `appModule` 绑 `single<BookMarkingGateway> { BookMarkingRepositoryImpl(get()) }`；
  `:app` 新增 `:domain:marking` / `:data:marking` 两个 Gradle 依赖。

五、测试：为什么必须有 Impl 测试

新增 **15 例**（`BookMarkingMapperTest` 9 + `BookMarkingRepositoryImplTest` 6）。
Impl 测试**不是锦上添花**：端口有 `Flow` 方法 `flowByBook`，把流内映射换成
`.map { it as List<BookMarking> }` **能编译**（只是一条 unchecked cast 告警），九个 mapper
用例**照样全绿**，真机每次发射才 `ClassCastException`（M4-3 立的判据）。故用假 DAO 驱动
**三次发射**并全部收集。
mapper 测试另有两条针对性的：可空字段（`chapterIndex` / `styleJson`）`null` 原样搬运、
`anchorJson` 首尾空白不可规范化（M4-4 的教训），以及一条**反向用例**（仅 `note` 不同的两条
不相等）——本域是全字段判等，整对象 `assertEquals` 成立，但没有反向用例就挡不住后来者补一个
id-only `equals`。

六、验证

- 单独 `clean` 后：四门禁全绿；`:app:compileAppDebugKotlin` + `testAppDebugUnitTest` +
  `assembleAppDebug` 全绿；`:domain:marking` / `:data:marking` 的 desktop 编译与测试通过
- 13 个模块的测试任务全绿，计数 **主验证集 714 不变 / 全量 1154 → 1169（+15）**，**0 失败**
- `lintAppDebug` 仍是迁移前就有的 **5 errors**（warnings 79 → 78，减少不是新增）
- 变异 **4 轮全红后回绿**：① `flowByBook` 流内映射退化成 unchecked cast；② `toDomain` 漏
  映射 `styleJson`；③ `getForChapter` 的 `chapterIndex` 不透传；④ `toDomain` 把可空
  `chapterIndex` 归一化成 0。每轮只精准打掉对应用例，全部经 `try/finally` + `atexit` 还原。
  ⚠️ 第 1 轮的锚点最初命中 2 次——KDoc 里写了同一句字面量（与 `portability-triage` 的
  「注释会干扰扫描」同源），加换行缩进后才唯一。

七、未验证

`:app` 侧 marking 的**运行期**行为仍无自动化覆盖：划线保存/更新/删除、目录 Sheet 笔记页
订阅、以及 `ContentProcessor` 的渲染合成路径（`toRenderProcess`）。本片能证明的是编译 +
门禁 + 打包 + 计数零偏离 + 变异敏感，不能替代在真机上划一条线并翻页看它是否画出来。
